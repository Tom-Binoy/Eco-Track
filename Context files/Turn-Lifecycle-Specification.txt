# Eco Track — Turn Lifecycle Specification (Consolidated, Phase 1)

> This document describes turn-by-turn behavior only. Authoritative field
> definitions for every table referenced below live in the schema document
> (`Final-Schema.txt`), which is the single source of truth for
> shapes/types. Where this doc previously restated full field lists, it now
> points back to the schema instead.

## 1. Context Assembly

Per `(userId, chatId)`, before the Gemini call:

- **Lean cached context** — `tonePreference`, `weightUnit`, `distanceUnit`, unresolved injuries, and `workoutContext`. Full profile details are read only through `Get_data`.
- **`workoutContext`** — latest row by `by_user`, `createdAt` desc, take 1.
- **`chats.cachedContext`** — if present and fresh (built at session start), reuse instead of re-fetching `profiles`/`workoutContext` above. Cache lives for the day, invalidated by daily-cleanup.
- **`messages`** — recent N rows via `by_chat`, ordered by `timestamp`. Always fetched fresh (cheapest, always-changing part).
- **`messageBlocks`** — fetch the persisted blocks for every raw message
  included above, ordered by message timestamp then block `order`. Send text
  and system-generated tool summaries to Gemini as the turn history. Raw tool
  requests/results, including invalid or failed calls, are retained only in
  internal `toolTraces` for authorized debugging and never reach Gemini,
  compression, or normal chat UI. `apiUsage` and `guideInvocations` are never
  included in Gemini context.
- **`sessionSummaries`** — via `by_chat_and_tier`, latest `compressedTill` per tier, used once raw messages exceed the token-size threshold.
- **Pinned card injection**: query `cards` for this chat where `inDiscussion === true`, then inject their `rawOutput`/`parsedData`. `messages.cardContext.closed` is UI decoration only and is never used for prompt injection.

## 2. The Gemini Call

Call 1 always uses `tools: [log_workout, Get_data, Correct_log,
search_exercise_library, calculate]`. `calculate` is always available and is
unrelated to naming guidance. Only while a naming-guide conversation is active
for the chat does its tools array also include `get_new_exercise_guidance` and
`create_custom_exercise`. A guide becomes active when
`search_exercise_library` returns still-ambiguous/near-miss results and Eco
enters a naming conversation; it clears on `resolved_existing`,
`resolved_custom`, or the existing 10-turn force-close in §7. Reuse §7's
trailing-marker streak as this active/inactive signal; do not introduce a
second parallel tracker. `responseSchema: { reply: string }`.
`log_workout` is create-only;
`Correct_log` owns every correction. If pinned cards are active, each is
labeled `"Card 1"`, `"Card 2"`, etc. (ephemeral, request-scoped mapping —
never a persisted or schema field) — model only ever sees/echoes labels,
never real `cards._id`s.

A Gemini response may contain multiple function requests. Persist every request
in its returned order. Execute independent read-only requests together; keep
writes and any request that relies on an earlier result ordered. Return every
executed result as function-response parts in one next model request, preserving
the corresponding request order. Every function response also carries the exact
`FunctionCall.id` of the request it answers; this correlation is required even
when several calls share the same function name. The same typed `Chat` instance
must continue the whole tool loop: the official `@google/genai` SDK retains the
full preceding model response, including Gemini 3's opaque `thoughtSignature`.
Do not manufacture or manually copy a `thoughtSignature` into a function
response. `log_workout` and `Correct_log` are normal
tool steps: validate, write when valid, return a truthful structured result,
then allow Gemini to decide the next work and eventually write the one natural
user reply. Invalid, malformed, or dependency-breaking requests return a
specific error result to Gemini rather than a backend-authored reply. The
special repeated general-`Get_data` containment rule is defined below.

The five-follow-up safety limit counts follow-up **model requests**, not the
number of function requests in a batch. A follow-up may carry all results from
one executed batch. The initial model request does not count; the fifth
follow-up is the final opportunity for Gemini to produce a natural response.
Every executed function result includes persisted `_ecoTurnControl` metadata
with the fresh-turn limit, completed request count, remaining request count,
and an instruction to finish when no requests remain. Gemini must use that
countdown without mentioning it to the user. If it still asks for more tool
work after that, the backend records the rejected call/result and closes the
turn with the existing conversational fallback, without Retry. This cap is
independent of the ten-turn naming-guide marker streak.

Eco must call `calculate` for any numeric output a user could reasonably
double-check later: 1RM estimates, percent-of-1RM back-calculations, plate
math, volume/tonnage totals, pace conversions, and unit conversions. It must
not calculate or state those numbers from its own reasoning. `expression` is a
last resort for pure arithmetic that does not fit a named operation; it must
never substitute for a named formula. If the applicable named operation is
uncertain, Eco prefers that named operation over guessing with `expression`.

`get_new_exercise_guidance` is disambiguation only, not a custom-exercise
namer. Its required Zod input is `{ rawPhrase: string, conversationDetail?:
string, candidates: Array<{
exerciseId, canonicalName, description, score }> }`, where candidates are
passed through from `search_exercise_library` (including a `description` field,
which is `null` when the library row has none) and capped at five;
`conversationDetail` carries concrete details gathered during the guide. Its return is exactly one
of: `{ outcome: "resolved_existing", exerciseId, aliasText? }`, `{ outcome:
"resolved_custom" }`, `{ outcome: "still_ambiguous" }`, or `{ outcome:
"declined_unsafe" }`. It writes no
`exerciseLibrary` or alias row. `resolved_existing` supplies the ID and,
only when the wording is a genuine alternate name worth saving, non-empty
`aliasText` for the next `log_workout`. Its write path creates or updates a
confirmed alias with `source: "confirmed"` only when that `aliasText` is
present; `resolved_custom` requires
`create_custom_exercise` next in the same ordered work sequence before `log_workout`; and
`still_ambiguous` permits no further tool call and leaves the guide active for
the next turn. `declined_unsafe` permits no further tool call, writes no card,
library row, or alias, and closes the guide conversationally. It still records
the same post-execution `guideInvocations` row as every other outcome. Eco must not call `create_custom_exercise` on the
`resolved_existing` path. During the guide, Eco walks the user through the
near-miss candidates conversationally rather than dumping a list. The required
backend-only `guideInvocations` review row is the sole post-execution write for
this guidance tool.

The guide's full behavioral content is injected at this tool invocation only:
it is included in the read-only resolver request and in the matching function
result returned to the main chat. It is not prepended to every guide-active
turn or retained as a permanent segment of the main system prompt.

`create_custom_exercise` takes required string `name` and `description` (both
are required in the tool declaration's schema),
optional string metadata (`category`, `equipment`, `muscleGroup`), optional
`allMuscles: string[]`, and optional `aliases: string[]`. It writes a personal
`exerciseLibrary` row only (`userId` is always the calling user, never global),
sets `source: "custom"`, builds `searchBlob` with the shared name/aliases/
description helper, immediately writes its `RETRIEVAL_DOCUMENT` embedding, and
returns a new `Library Exercise N` label while retaining the library ID internally. Its aliases seed `exerciseLibrary.aliases` only;
it never writes `userExerciseAliases`. Eco must receive that label
before calling `log_workout` in the same turn; these dependent tool requests
remain ordered within the five-follow-up model-request cap. Before invoking it, Eco must have
established through the guide conversation that the user consents to keeping
the movement custom and that it is not a real exercise under another name.
This precondition is prompt-enforced, not backend-validated.

`Get_data` never accepts a session/database ID. It has no `collectionType`
field: the supplied optional arguments determine what is read. Its contract is:

- `collectionPoints`: an optional array of requested profile fields. Allowed
  values are `name`, `injuries`, `equipment`, `goals`, `trainingPattern`,
  `skillLevel`, `weightUnit`, and `distanceUnit`.
- `dailySummaryDate`: an optional local calendar date in `YYYY-MM-DD` format.
  It reads that user's daily summary for that exact date and returns only
  `{ date, content }`, or `null` if no summary exists.
- `dateRange`: an optional `{ startDate, endDate }` range for historical
  workout lookup. The first call returns chronologically ordered, ephemeral
  `History Exercise 1`, `History Exercise 2`, etc. labels.
- `exerciseId`: optional and only meaningful with `dateRange`; it must be one
  of the returned `History Exercise N` labels and returns that exercise's details.

The tool result always has `profile`, `dailySummary`, and `exercises` keys.
`Correct_log` may target a pinned card, or a historical `History Exercise N` only after
that `Get_data` flow has returned it. Any of these read requests may be
combined in one call, but Eco must not request data speculatively.

At most one general `Get_data` request runs in a turn. A general request is one
for profile fields, a daily summary, or a date range; it must batch every needed
general read. The sole permitted later lookup is `exerciseId: "History Exercise N"`
after that turn's date-range response. If Gemini requests another general
lookup, persist its raw rejected request/result in internal `toolTraces`, write
a safe rejection summary in `messageBlocks`, and record a `redundant_data_lookup`
debug warning. Do not execute it; finish with the existing local conversational
fallback rather than failing the message or showing Retry.

`calculate` is pure computation: no database reads or writes, no profile
unit-preference lookup, and no external calls. Every success returns
`{ operation, result, ...operationSpecificFields }`; invalid numeric domains
and validation failures return `{ operation, result: null, error: { code,
message } }` rather than throwing. Its Zod input is a discriminated union on
`operation`:

- `oneRepMax`: `{ formula: "epley" | "brzycki", weight: number, reps: int >=
  1, weightUnit: "kg" | "lbs" }`. Epley is `weight * (1 + reps / 30)`;
  Brzycki is `weight * (36 / (37 - reps))`. Reject Brzycki `reps >= 37`.
- `percentOf1RM`: `{ oneRepMax: number, percent: number (0–100) }`. Return the
  percentage rounded to the nearest `0.5`.
- `convertUnit`: `{ value: number, from: "kg" | "lbs" | "km" | "miles",
  to: same enum }`. Reject cross-family conversion. Use `1 kg = 2.2046226218
  lbs` and `1 mile = 1.609344 km`.
- `plateMath`: `{ targetWeight: number, barWeight: number, weightUnit: "kg" |
  "lbs", availablePlates?: number[] }`. Bar weight is required, never assumed.
  Defaults are kg `[25,20,15,10,5,2.5,1.25]` and lbs `[45,35,25,10,5,2.5]`.
  Return greedy largest-first plates per side and the actual achievable total;
  never silently round the target.
- `volumeTotal`: `{ sets: Array<{ reps: number, weight: number }> }`, minimum
  one set. Return `sum(reps * weight)` and `setCount`.
- `paceConvert`: `{ distance: number, distanceUnit: "km" | "miles", duration:
  number }`, where duration is seconds. Return seconds-per-unit and formatted
  `"M:SS per km/mile"`; reject non-positive distance.
- `expression`: `{ expression: string }`, only for pure arithmetic outside the
  named operations—never formula recall. It permits only numbers,
  parentheses, `+ - * / %`, and `sqrt`, `round`, `floor`, `ceil`, `min`, `max`,
  `pow`, and `abs`; it never uses `eval()` or `Function()`.

BMI, TDEE, and calorie estimation are out of V1 scope.

Response either includes zero or more function requests, or text only. A batch
of tool requests is followed by one function-response message containing every
executed result; Gemini then chooses the next batch or the final reply.

## 3. Post-Call Validation

Create the Eco `messages` row when processing starts, then complete its
`ecoText` when the response is available. The client may observe this row and
its `messageBlocks` trace reactively while processing continues.

If startup or a tool continuation fails, complete that row with the generic
unavailable message and retain the detailed non-secret cause only in action
logs/debug events. The latest failed turn locks the chat input; Retry reuses
that message ID and stored user text, clears its partial `messageBlocks`, and
does not create another `messages` row. Historic locally fabricated assistant
fallback text is omitted from regenerated Gemini history, while the associated
persisted tool summaries remain available. Full raw payloads remain private
debug traces only.

- **No tool request** → done, return `reply`.
- **Tool request fired** → run deterministic Zod validation (types, ranges, enum
  membership, and required resolved exercise IDs).

`log_workout` validation covers types, ranges, block enums, and a non-empty
`exerciseId` on every extracted exercise. A missing or empty `exerciseId` is
the same validation failure as any malformed type, range, or enum value: it
returns a specific tool result to Gemini and creates no card. The write branch
is unreachable until this validation passes.
`needsClarification` determines whether a valid extraction auto-confirms or
creates a pending card. Vague exercise references are handled conversationally:
Eco asks for a concrete exercise name and does not call `log_workout`, so there
is no generic-phrase field or generic-phrase card path. A validation failure
also produces a conversational clarification instead of a card. A resolved
block carries canonical `exerciseId` values. `create_custom_exercise` is the
deliberate exception to confirmation-only library creation and supplies its
new personal `Library Exercise N` label before `log_workout`.

## 4. Write Branch

1. Resolve every concrete extracted exercise: aliases resolve immediately; an
   alias miss uses the batched turn loop (`search_exercise_library` then
   `get_new_exercise_guidance` and `create_custom_exercise` when needed).
   Independent read-only searches can share a batch; each dependent step stays
   ordered. The five-follow-up cap counts model requests after result batches,
   not individual tool requests. Each executed result carries persisted
   `_ecoTurnControl` countdown metadata, and Gemini must reply naturally when
   its remaining count reaches zero. The cap is independent of the §7 ten-turn
   naming-guide marker streak; neither counter increments the other.
   Before logging any exercise whose canonical identity Eco cannot already
   resolve through a known alias, it proactively calls the read-only
   `search_exercise_library`; it does not ask permission mid-turn. This search
   commits nothing — user consent remains at card confirmation.
   The guidance tool needs no separate consent flag. The latter tool is the
   sole deliberate exception to confirmation-only custom-library creation: it
   creates and embeds a personal, description-required row before
   `log_workout`; it never creates a global row or an alias-table row.
   `search_exercise_library` is read-only: it uses the shared
   confirmed-alias normalizer, then checks an exact alias, user-alias vectors,
   and separate personal/global library vectors in that order. The one
   `RETRIEVAL_QUERY` embedding is reused for both library searches; each vector
   search takes five hits, personal wins an exact score tie, and 0.82 is the
   auto-resolution threshold. It accepts up to five queries per request and
   returns only `Library Exercise N` labels, canonical names, descriptions, and
   scores; raw library IDs remain in chat-scoped `exerciseSearchReferences`.
   Labels resolve for the search turn plus three later user turns, then their
   references are deleted and a fresh search is required. Below threshold it returns up to five ranked
   near-misses for Eco to handle conversationally. Generic wording
   never reaches this branch because Eco asks for a concrete name instead.
   Immediately after each executed `get_new_exercise_guidance` call, write one
   backend-only `guideInvocations`
   row with the turn's `userId` and `messageId`, `reviewed: false`, and
   `createdAt`. This write is not model-invoked and is not included in any tool
   return schema.
2. `still_ambiguous` also stays plain conversation. It writes neither a card
   nor an alias. `declined_unsafe` likewise writes neither, but closes the
   guide rather than leaving it active. At most one naming conversation may be
   active in a chat. Injury-specific declines use the existing lean
   `profiles.injuries` context; universal safety declines are model judgment,
   so this safety-tier split needs no schema field.
3. Each fully resolved block writes atomically. With `needsClarification:
   true`, it writes one **pending** card only. Otherwise it creates its
   confirmed card plus session, block, and exercises immediately. It creates
   or updates a user alias only for an exercise carrying non-empty `aliasText`.
   A
   multi-exercise message may create multiple cards while an unresolved sibling
   writes nothing.
4. Confirm receives only already-resolved canonical or personal-custom
   `exerciseId` values. It never creates an `exerciseLibrary` row as a fallback;
   it writes the session, blocks, and exercises for a pending card, and creates
   or updates a confirmed alias only when that exercise carries non-empty
   `aliasText`; it backfills `sessionId` and flips the card to `confirmed`.
5. Historical `Correct_log` always creates a pending card with
   `correctsBlockId`; its confirm replaces the target block only after explicit
   re-confirmation.

## 5. Cards — Behavior

- **Direct manual edits**: instant, local, no state transition needed — user edits fields, taps confirm, write happens same as normal confirm flow.
- **Ask Eco**: available on both `pending` and `confirmed` cards. Sets `inDiscussion: true`. Card is isolated in UI (expanded, pinned open) regardless of starting state. The active discussion is also signalled by a visually distinct banner directly above the chat text input.
  - Pure clarification → no state change. Only the explicit **Back to deck** control in that input-area banner calls `bringCardBackToDeck` and flips `inDiscussion` false.
  - Correction on a `pending` card → patch `rawOutput`/`parsedData` in place, stays `pending`, awaits confirm as normal.
  - Correction on a `confirmed` card → patch `cards`, but do **not** silently rewrite `exercises` — flip back to a re-confirm state, show diff, only write to `exercises` on explicit re-confirm.
- **Multi-card pin (v2+)**: explicit user multi-select, not model-inferred — sidesteps ambiguity. Uses the same ephemeral `"Card N"` labeling already built for v1 single-card flow.

## 6. Messages — Card Context Behavior

- A `cardContext` closure entry is written exactly once by the explicit **Back
  to deck** action in the input-area discussion banner, on the card's source
  message.
- It drives the UI closure chip only; prompt injection reads `cards.inDiscussion`.

## 7. Naming-guide and trace persistence

- The backend writes `exercise_naming_guide_active` to `messages.usedTools` on
  every guide turn. A real `get_new_exercise_guidance` call is recorded by
  name as well.
- Context assembly counts the trailing marker streak from already-fetched
  messages. This streak is the sole naming-guide active/inactive signal: it
  begins when `search_exercise_library` returns still-ambiguous/near-miss
  results and Eco enters naming guidance, and ends on `resolved_existing`,
  `resolved_custom`, `declined_unsafe`, or force-close. At 8 turns it nudges resolution; at 10 it
  force-closes under the raw name without saving an alias. No second tracker is
  created.
- `guideInvocations` is a safety/tuning review log only. It is written once
  after each executed `get_new_exercise_guidance` call, is never sent to
  Gemini, and does not replace
  the `messages.usedTools` trailing-marker signal for active naming guidance.
- Eco stores the user's wording as an alias only when it is a genuine alternate
  name for the same movement. Vague, sloppy, or non-alternate wording is not
  stored as an alias; Eco pivots to the canonical name in its reply instead.
- The resolver includes optional `aliasText` only on `resolved_existing` when
  that condition holds. `log_workout` carries it per exercise to the confirmed
  write path; it is never inferred from `exercises.name`.
- `exercises.name` remains the raw extracted string. Card-query display data
  returns both `displayedName` and `canonicalName`: canonical is the default,
  while a matching user alias displays the raw stored wording. Workout-card
  exercise rows render `displayedName` as the primary name and render the
  canonical name as a clearly legible secondary line only when the two names
  differ.
- `messageBlocks` are written in order as text and `tool_summary` notes. The
  notes are client-visible and are the persisted main-turn Gemini history.
  Invalid or failed calls receive a safe concise note. Full requests/results are
  written to internal-only `toolTraces`; they are never sent to Gemini.
  Token/cost records in `apiUsage` remain backend-only.

## 8. Memory / Reflection Triggers

- **`sessionSummaries` compression**: a token/size-estimate threshold on the
  compressible raw messages and their persisted text/tool-summary `messageBlocks`
  (not message count or time-based) is scheduled post-turn, non-blocking, once
  Gemini has completed the message; it is never scheduled between tool calls.
  Tier 1 receives each source message’s ordered text/tool-summary history; Tier 2 receives
  the resulting Tier 1 summaries and therefore retains material tool outcomes.
  Failed or invalid tool results must be represented when they affect recovery
  or an unresolved thread. Neither tier receives `apiUsage`. Progress is tracked
  cumulatively via `compressedTill`. When at least six Tier 1 rows exist, Tier
  2 compacts exactly the five oldest Tier 1 rows, retaining the sixth and any
  newer rows; existing Tier 2 rows are not re-compressed by this v1 mechanism.
- **Daily cleanup** (`dailySummaries`, profile update, `workoutContext`): one hourly, local-midnight trigger; no session-close trigger. It skips only when no `chats` row exists for `(userId, today's local date)`; inactive days therefore do not create summaries. An existing `dailySummaries` row for that date is retry-safety only, not the real app gate.
- Daily cleanup makes exactly one Gemini call. Its input order is: daily-cleanup system prompt; full profile; latest workout context; daily summaries; remaining tier 1 and tier 2 session summaries in chronological order; and the uncompressed raw-message tail in chronological order. Both tiers are included; a raw message covered by `compressedTill` is never included again.
- The daily-summary window is the larger of (a) every retained summary after the latest workout-context row's `sourceDailySummaryId`, or (b) the two most recent available daily summaries. If fewer than two exist, inject all available summaries. A recent context update therefore cannot shrink the journal evidence below this floor, while a context that has gone unchanged for longer receives all accumulated summaries.
- The response contains a daily summary plus optional typed profile and workout-context replacements. The model alone decides whether `workoutContext` is `null`; when null, no row is written and subsequent cleanup calls continue accumulating daily summaries from the last context update. Profile updates are limited to explicit changes in goals, equipment, training pattern/availability, skill level, or injuries. Each injury has a stable `injuryId`; updates must target that ID, never a description match.
- The daily summary, optional profile patch, and optional workout-context row commit together before the cron purges that day's `sessionSummaries` and invalidates today's cached chat context.

## 9. Context Caching

- `chats.cachedContext` / `cachedContextAt` — lean bundle of tone/unit
  preferences, active injuries, and `workoutContext`, built once per chat/day
  and invalidated by daily-cleanup.
- Gemini-side prompt/context caching — deferred post-v1, revisit once the static system prompt is finalized and its real token weight is known.

## 10. Explicitly Deferred

- Multi-card free-text "Ask Eco" (ambiguous card resolution) — deferred to pin feature (explicit multi-select avoids the ambiguity).
- Message editing beyond "most recent message only" — no tree/fork structure for daily chat, ever. Fork as a distinct, deliberate future feature for blueprint/analysis, not derived from chat editing.
- `messageFeedback` aggregate analytics, git-style history — previously deferred, unchanged.

The one-chat-per-user-per-day rule removes the formerly open mid-day cache
question: a newly created chat always builds its own cache.
