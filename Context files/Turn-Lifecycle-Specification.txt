# Eco Track — Turn Lifecycle Specification (Consolidated, Phase 1)

> This document describes turn-by-turn behavior only. Authoritative field
> definitions for every table referenced below live in the schema document
> (`eco_track_schema_phase7.md`), which is the single source of truth for
> shapes/types. Where this doc previously restated full field lists, it now
> points back to the schema instead.

## 1. Context Assembly

Per `(userId, chatId)`, before the Gemini call:

- **`profiles`** (by `by_userId`) — `equipment`, `goals`, `injuries`, `skillLevel`, `trainingPattern`, `tonePreference`, `weightUnit`/`distanceUnit`, `timezone`.
- **`workoutContext`** — latest row by `by_user`, `createdAt` desc, take 1.
- **`chats.cachedContext`** — if present and fresh (built at session start), reuse instead of re-fetching `profiles`/`workoutContext` above. Cache lives for the day, invalidated by daily-check.
- **`messages`** — recent N rows via `by_chat`, ordered by `timestamp`. Always fetched fresh (cheapest, always-changing part).
- **`sessionSummaries`** — via `by_chat_and_tier`, latest `compressedTill` per tier, used once raw messages exceed the token-size threshold.
- **Pinned card injection**: if the latest `messages.cardContext` has any entries with `closed: false`, fetch those `cards._id` rows fresh and inject their `rawOutput`/`parsedData` into this turn's prompt. Cards with `closed: true` are shown once (this closure turn) then never injected or rendered again.

## 2. The Gemini Call

One request. `tools: [log_workout]`, `responseSchema` set. If pinned cards are active, each is labeled `"Card 1"`, `"Card 2"`, etc. (ephemeral, request-scoped mapping — never a persisted or schema field) — model only ever sees/echoes labels, never real `cards._id`s.

Response either:
- **(a)** includes a `functionCall` (args = parse data) → logging/correction turn.
- **(b)** text only → conversational/query turn.

## 3. Post-Call Validation

Write a `messages` row regardless of branch (see schema for the full field list).

- **No tool call** → done, return `reply`.
- **Tool call fired** → run deterministic Zod validation (types, ranges, enum membership).

| Validator | Model's `needsClarification` | Effective path |
|---|---|---|
| pass | false | high confidence |
| pass | true | low confidence |
| fail | either | low confidence (validator overrides model) |

Validator failure is UX-identical to low confidence — no separate error state.

## 4. Write Branch

**High confidence:**
1. Find/create `sessions` row (`by_user_date`).
2. Write `blocks` (`sessionId`, `userId` denormalized, `types`, `order`).
3. Write `exercises` (`blockId`, `userId` denormalized, `name`, `sets[]`, `order`).
4. Write `cards` as confirmed, with `sessionId` set.
5. Set `messages.sessionId`.

**Low confidence:**
1. Write `cards` only, as pending, with `sessionId` left unset.
2. No `sessions`/`blocks`/`exercises` writes.
3. User confirm (direct mutation, no AI) later performs steps 1–3 above, backfills `cards.sessionId`, flips `state → "confirmed"`.

## 5. Cards — Behavior

- **Direct manual edits**: instant, local, no state transition needed — user edits fields, taps confirm, write happens same as normal confirm flow.
- **Ask Eco**: available on both `pending` and `confirmed` cards. Sets `inDiscussion: true`. Card is isolated in UI (expanded, pinned open) regardless of starting state.
  - Pure clarification → no state change, `inDiscussion` eventually flips false.
  - Correction on a `pending` card → patch `rawOutput`/`parsedData` in place, stays `pending`, awaits confirm as normal.
  - Correction on a `confirmed` card → patch `cards`, but do **not** silently rewrite `exercises` — flip back to a re-confirm state, show diff, only write to `exercises` on explicit re-confirm.
- **Multi-card pin (v2+)**: explicit user multi-select, not model-inferred — sidesteps ambiguity. Uses the same ephemeral `"Card N"` labeling already built for v1 single-card flow.

## 6. Messages — Card Context Behavior

- One `cardContext` entry per pinned/discussed card active as of that turn.
- `closed: true` appears exactly once, on the turn where that card's discussion ends.
- Drives both: (a) next turn's prompt — "Card 2 has been closed," stop injecting it; (b) UI — chip renders once on the closure message, then falls off permanently.

## 7. Memory / Reflection Triggers

- **`sessionSummaries` compression**: token/size-estimate threshold on raw `messages` for a chat (not message count, not time-based). Fires post-turn, non-blocking. Tracked cumulatively via `compressedTill`.
- **`dailySummaries` + `workoutContext`**: single daily-check trigger (no separate session-close). Runs via hourly cron: bucket by `profiles.timezone` (IANA string), find zones currently at local midnight, run daily-check only for users in those zones. Idempotency guard: skip if `dailySummaries` already exists for `(userId, today's local date)`.
- Same cron also: purges that day's `sessionSummaries` rows once `dailySummaries` is written, and evaluates/updates `workoutContext` at the same time.

## 8. Context Caching

- `chats.cachedContext` / `cachedContextAt` — snapshot of `profiles`+`workoutContext`, built once per chat/day, invalidated by daily-check. Avoids re-querying rarely-changing data every turn.
- Gemini-side prompt/context caching — deferred post-v1, revisit once the static system prompt is finalized and its real token weight is known.

## 9. Explicitly Deferred

- Multi-card free-text "Ask Eco" (ambiguous card resolution) — deferred to pin feature (explicit multi-select avoids the ambiguity).
- Message editing beyond "most recent message only" — no tree/fork structure for daily chat, ever. Fork as a distinct, deliberate future feature for blueprint/analysis, not derived from chat editing.
- `messageFeedback` aggregate analytics, git-style history — previously deferred, unchanged.
