# Eco Track — Final Compiled Schema (Phase 7)

Convex schema for Eco Track, a conversational AI workout logging app.
This document compiles all decisions from Phases 1–6, plus the schema-relevant
decisions surfaced in the Turn Lifecycle Specification (consolidated). Notes are
embedded as comments directly in the schema so context travels with the field
it explains. This document is schema-only — turn-by-turn behavior lives in the
Turn Lifecycle Specification.

---

## Changelog since Phase 6

Reconciled against the Turn Lifecycle Spec (consolidated):

- **`cards.sessionId`** — now optional. Low-confidence cards are written
  without a session until user confirm backfills it.
- **`cards.state`** — `"editing"` removed. Only `"pending" | "confirmed"`
  remain; direct manual edits no longer need a distinct state.
- **`cards.order`** — added. Display/label order, set at creation; also
  backs the ephemeral "Card N" prompt-labeling scheme.
- **`cards.inDiscussion`** — added. `boolean`, true while a card is under
  an active Ask Eco conversation.
- **`messages.cardContext`** — added. Optional array tracking which cards
  were pinned/discussed on that turn, and which closed.
- **`sessionSummaries.compressCount` → `compressedTill`** — replaced with a
  timestamp of the last raw message covered (cumulative across tiers);
  `compressCount` was unneeded duplication.
- **`chats.cachedContext` / `chats.cachedContextAt`** — added. Snapshot of
  `profiles` + `workoutContext`, built once per chat/day, invalidated by
  the daily-check cron.
- **`workoutContext.triggerReason`** — narrowed to `"daily-check"` only.
  `"session-close"` removed: there is no separate session-close trigger:
  a single hourly cron drives both `dailySummaries` and `workoutContext`.
- **Lean chat cache** — `chats.cachedContext` now holds only tone and unit
  preferences, active injuries, and `workoutContext`; it is no longer a full
  `profiles` snapshot.
- **Exercise identity** — `exerciseLibrary` and `userExerciseAliases` were
  added, with separate `exerciseLibraryEmbeddings` and
  `userExerciseAliasEmbeddings` tables for 768-dimension semantic resolution.
  Every logged `exercises` row now has the required `exerciseId` FK; its `name`
  remains the original extracted string. Display responses carry both a
  canonical name and a displayed name; the latter uses matching user-alias
  wording while the former remains available for later UI treatment.
- **Corrections and trace** — `cards.correctsBlockId`, `messages.usedTools`,
  and summary-only `messageBlocks` support historical corrections, guide
  history, client-visible activity, main-turn Gemini context, and Tier-1
  compression. Internal `toolTraces` retain the corresponding raw payloads for
  authorized debugging only.
- **Naming-guide tool availability (reversal)** — guide-active state gates
  availability of `get_new_exercise_guidance`; this reverses the prior lock
  that the guide system lived in the standard Call 1 toolset with no
  conditional-unlocking flag. `create_custom_exercise` is new and is gated by
  the same guide-active state. The always-available Call 1 tools are unchanged:
  `log_workout`, `Get_data`, `Correct_log`, and `search_exercise_library`.
  No separate table or field stores live naming-guide state: the trailing
  `messages.usedTools` guide-marker streak is the sole active/inactive signal.
  `discussionType`, `guideActiveTurns`, and `hiddenTrace` are intentionally
  absent.
- **Naming-guide safety outcomes** — `declined_unsafe` is an outcome contract,
  not persisted state. It needs no schema change: injury-specific evaluation
  uses the existing lean `profiles.injuries` context and universal safety is a
  model judgment. It closes conversationally without a card, library row, or
  alias; its executed guidance call still has the usual `guideInvocations` row.
- **Naming-guide prompt injection** — the guide's behavioral content is not
  permanent main system-prompt state. It is supplied only with an executed
  `get_new_exercise_guidance` resolver/function-result exchange. Its tool input
  has `rawPhrase`, optional gathered `conversationDetail`, and up to five exact
  candidates including nullable descriptions; this remains a prompt/tool
  contract, not persisted schema state.
- **`messageBlocks` now read into context/compression (reversal)** —
  earlier phases treated `messageBlocks` as presentation-only, never read by
  the model. They now provide text and tool-summary turn history during context
  assembly (Turn Lifecycle Spec §1) and Tier-1 compression (Turn Lifecycle
  Spec §8). Full historical notes are fed in—not scoped to just an active
  naming-guide window. Raw tool payloads live only in `toolTraces`; `apiUsage`
  also remains backend-only.
- **wger catalogue** — global library rows retain `wgerId`; it is the
  idempotent upsert key for the public wger seed action.

## Global identity note

`userId` is `v.id("profiles")` everywhere, **except** `profiles.userId`
itself, which is the one exception — the foreign key *to* Convex Auth,
the root of the identity chain.

## Full Schema

```
profiles: {
  userId                   // FK -> Convex Auth users (the one exception to the userId rule above)
  name                     // string
  createdAt                // number (timestamp)

  injuries                 // array of { injuryId, description, status, notedAt }
  equipment                // string, comma-separated, injected as-is
  goals                    // string, comma-separated, injected as-is
  trainingAvailability     // { daysPerWeek, sessionLength }
  tonePreference           // string
  weightUnit               // "kg" | "lbs"
  distanceUnit             // "miles" | "km"
  darkMode                 // boolean
  // ^ darkMode + weightUnit absorbed the old `userPreferences` table — folded in because it queried the same way as profiles already did.
timezone   // string, IANA identifier (e.g. "Europe/London")
           // required. Set during onboarding (device-detected, same moment as weightUnit/distanceUnit/darkMode in Task 2).
           // Read by Turn Lifecycle §1 (context assembly) and §7 (daily-check cron bucketing).

  skillLevel: {
    strength, flexibility, endurance,
    calisthenicsSkills, sportSpecific, bodyComposition   // all strings
  }
  trainingPattern          // string
}
.index('by_userId', ['userId'])   // Convex Auth lookup on login

// CASCADE: deleting a profile cascades every table below EXCEPT userReports.


chats: {
  userId              // FK -> profiles
  date                // string "2026-06-29"
  createdAt           // number (timestamp)
  cachedContext        // optional lean object: tonePreference, weightUnit,
                        // distanceUnit, activeInjuries, workoutContext.
                        // Built once per chat/day; full profile data is read
                        // on demand through Get_data.
  cachedContextAt       // optional number (timestamp) — invalidated by the
                        // daily-check cron (see workoutContext / dailySummaries
                        // below). No separate index needed; read alongside the
                        // chat row itself.
  // One chat exists per user per local day. A newly created chat always builds
  // its own fresh cache, so there is no same-day second-chat stale-cache case
  // to handle (Turn Lifecycle Specification §10).
}
.index('by_user_date', ['userId', 'date'])
  // Compound index does double duty: (1) everyday "load this user's chat
  // list," and (2) the per-user retention sweep below. No separate
  // by_date index needed since the sweep is always scoped to one userId.

// CASCADE: chats has TWO deletion paths with DIFFERENT cascade lists —
// this is intentional, not an inconsistency. Why: a scheduled sweep is a
// storage-management decision and shouldn't touch the journal layer; a
// force-delete is an intent-to-erase decision and should take the journal
// with it. Same parent, same child tables, different lists depending on
// *why* the deletion happened — a value that has to live in which
// mutation gets called, not in the schema itself.
//
//   1. Retention sweep (automatic, per-user, weekly-since-last-check, 1yr window)
//      -> cascades: messages, cards, sessionSummaries, messageFeedback (transitively)
//      -> does NOT cascade dailySummaries (survives, chatId left dangling on purpose)
//      -> implemented as its own mutation (e.g. sweepOldChats), triggered as a
//         side effect of that user's login if 7+ days since last check.
//         A user who never returns never gets swept — accepted tradeoff.
//      -> NOTE: deliberately paused for now (no code path currently invokes
//         it) — don't re-enable until there are real users, v3+.
//
//   2. Force delete (user-initiated "delete this chat," or admin action)
//      -> cascades everything the sweep does, PLUS dailySummaries
//      -> implemented as a separate mutation (e.g. forceDeleteChat)
//
//   Kept as two separate mutations rather than one parameterized
//   deleteChat(hard: boolean) — flagged so a future refactor doesn't
//   accidentally collapse them and lose the distinction.
//
//   cachedContext / cachedContextAt are ordinary fields on the chats row
//   itself, so both deletion paths remove them for free — no separate
//   cascade handling required.


messages: {
  chatId        // FK -> chats
  userText      // string
  ecoText       // string
  sessionId     // optional FK -> sessions
  timestamp     // number
  cardContext   // optional array of { cardId, order, closed: boolean }
                // UI decoration only. closed: true is written once by the
                // explicit “bring card back to deck” action; it never drives
                // prompt injection.
  usedTools     // optional string[] of real tool names invoked this turn,
                // plus the backend-only exercise_naming_guide_active marker;
                // historical trace only, not a live guide-state field.
}
.index('by_chat', ['chatId'])
.index('by_session', ['sessionId'])

// CASCADE: deleted whenever parent chat is deleted, under BOTH paths.
// messages deletion cascades messageFeedback in turn (see messageFeedback
// note below — no standalone message-deletion path exists elsewhere).


cards: {
  chatId        // FK -> chats
  messageId     // FK -> messages
  sessionId     // optional FK -> sessions — undefined until a low-confidence
                // card is confirmed, at which point confirm backfills it.
  rawOutput     // string, exact Gemini JSON
  parsedData    // object, structured interpretation
  state         // "pending" | "confirmed"
                // "editing" removed entirely — direct manual edits are
                // instant/local (user edits fields, taps confirm, same
                // write path as a normal confirm) and need no distinct state.
  order         // number, display/label order, set at creation — also backs
                // the ephemeral "Card N" request-scoped labeling used when
                // multiple cards are pinned in a prompt (never persisted
                // as a schema field on the model side, just this order value).
  inDiscussion  // boolean, true while this card is under an active Ask Eco
                // conversation. Ask Eco is available on both pending and
                // confirmed cards; a correction on a confirmed card patches
                // this row but does not silently rewrite exercises — it
                // waits for an explicit re-confirm.
  correctsBlockId // optional FK -> blocks. Set only on a pending historical
                  // correction; confirm replaces that block rather than
                  // silently rewriting a committed workout.
  createdAt     // number (timestamp)
}
.index('by_chat', ['chatId'])
.index('by_session', ['sessionId'])   // TEMPORARY — safe to drop post-growth-phase, no dependents
.index('by_message', ['messageId'])   // TEMPORARY — safe to drop post-growth-phase, no dependents
// ^ flagged three times now (Phase 4, 5, 7) — worth actually scheduling
//   a removal date rather than leaving as a permanent "temporary."

// CASCADE: deleted whenever parent chat is deleted, under BOTH paths.
// sessionId being optional doesn't change this — cascade is keyed off
// chatId, not sessionId.


sessions: {
  userId        // FK -> profiles
  date          // string "2026-06-29"
  notes         // optional string
  createdAt     // number (timestamp)
}
.index('by_user_date', ['userId', 'date'])

// CASCADE: never deleted by the app itself — the permanent workout record
// layer. Only removed transitively via a profiles deletion. No scheduled
// deletion path exists; manual/admin deletion is an edge case, not a
// designed feature. This also guarantees workoutContext.sourceSessionId
// can never dangle.


blocks: {
  sessionId         // FK -> sessions
  userId            // FK -> profiles  [DENORMALIZED, not indexed]
                     // Write-once, structurally cannot drift: no mutation
                     // exists anywhere in the schema to reassign
                     // blocks.sessionId, so there's no path that could
                     // cause the denormalized copy to diverge from the
                     // value reachable via the transitive chain. This is
                     // a structural guarantee, not an operational one.
                     // FUTURE-PROOFING FLAG: if a "move block to a
                     // different session" feature is ever added (not
                     // currently planned), it would need to update this
                     // denormalized userId on the block AND every
                     // exercise beneath it as part of the same operation.
  types             // array of block type literals (not indexed)
  intervalSeconds   // optional number
  order             // number
  createdAt         // number (timestamp)
}
.index('by_session', ['sessionId'])

// CASCADE: deleted transitively via sessions -> profiles.


exercises: {
  blockId       // FK -> blocks
  userId        // FK -> profiles  [DENORMALIZED, not indexed]
                // Same write-once/no-drift guarantee as blocks.userId
                // above — no mutation exists to reassign exercises.blockId.
  exerciseId    // REQUIRED FK -> exerciseLibrary. A logged instance's row ID
                // is distinct from this reusable canonical identity.
  name          // raw extracted string; never simplified in place
  weightUnit    // optional "kg" | "lbs"
  order         // number
  sets          // array of { reps?, weight?, duration?, distance? }
  createdAt     // number (timestamp)
}
.index('by_block', ['blockId'])
.index('by_exercise', ['exerciseId'])
.index('by_user_and_name', ['userId', 'name'])

// CASCADE: deleted transitively via blocks -> sessions -> profiles.


exerciseLibrary: {
  canonicalName // string
  aliases       // string[]
  searchBlob    // canonicalName + aliases + description when present, kept in sync on every write
  userId        // optional FK -> profiles; undefined means global wger entry
  category, equipment, muscleGroup, description // optional string metadata
  allMuscles    // optional string[] metadata
  source        // "wger" | "custom"
  wgerId        // optional number
  createdAt     // number
}
.index('by_wgerId', ['wgerId']) // idempotent global wger seed/upsert lookup
.index('by_user', ['userId'])

exerciseLibraryEmbeddings: {
  exerciseId    // FK -> exerciseLibrary
  userId        // optional FK -> profiles; mirrors the source library row
  equipment, muscleGroup // optional copied filter fields
  embedding     // 768-dimension gemini-embedding-001 document vector
  createdAt     // number
}
.index('by_exercise', ['exerciseId'])
.vectorIndex('by_embedding', { vectorField: 'embedding', dimensions: 768,
  filterFields: ['userId', 'equipment', 'muscleGroup'] })

// Embeddings stay out of the main library row so normal reads remain lean.
// There is intentionally no full-text search index: resolution uses vectors.

// Global rows are never deleted for a profile. Custom rows cascade with their
// owning profile.
// NOTE: duplicate/near-duplicate custom entries per user (e.g. two slightly
// different "Bulgarian split squat" rows) are a known, accepted v1 gap —
// explicitly pushed to v2, not a bug to fix now.

userExerciseAliases: {
  userId              // FK -> profiles
  rawInputNormalized  // string
  exerciseId          // FK -> exerciseLibrary
  source              // "confirmed" | "auto"
  createdAt, lastUsedAt // number timestamps
}
.index('by_user_and_raw', ['userId', 'rawInputNormalized'])

// Created or updated at a confirmed write only when per-exercise aliasText is
// non-empty. aliasText is resolver/model-provided for genuine alternate names;
// it is never inferred from exercises.name.

// CASCADE: deleted with its profile.

userExerciseAliasEmbeddings: {
  aliasId       // FK -> userExerciseAliases
  userId        // FK -> profiles
  embedding     // 768-dimension gemini-embedding-001 document vector
  createdAt     // number
}
.index('by_alias', ['aliasId'])
.vectorIndex('by_embedding', { vectorField: 'embedding', dimensions: 768,
  filterFields: ['userId'] })

// CASCADE: deleted with its profile.

messageBlocks: {
  messageId   // FK -> messages
  order       // number, chronological within the response trace
  type        // "text" | "tool_summary"
  content     // string
  toolName    // optional string
  createdAt   // number
}
.index('by_message', ['messageId'])

// messageBlocks is read into Gemini context and tier-1 compression, as well
// as remaining client-visible for the processing activity UI. It never stores
// raw tool payloads; invalid/failed calls become safe concise summary notes.

toolTraces: {
  messageId       // FK -> messages
  userId          // FK -> profiles
  order           // number, execution order within the message
  toolName        // string
  functionCallId  // optional SDK correlation ID
  requestJson     // raw private request payload
  resultJson      // optional raw private result payload
  status          // "pending" | "completed" | "rejected"
  createdAt       // number
  completedAt     // optional number
}
.index('by_message', ['messageId'])
.index('by_user_and_message', ['userId', 'messageId'])

// Internal-only debug data. Never returned by normal chat queries, included in
// Gemini history, or passed to compression. Cascades with its parent message
// under both chat-deletion paths.

exerciseSearchReferences: {
  chatId, userId, messageId // FKs -> chats, profiles, messages
  exerciseLibraryId         // FK -> exerciseLibrary; never exposed to Gemini
  label                     // chat-scoped "Library Exercise N"
  canonicalName, description, createdAt
}
.index('by_chat', ['chatId'])
.index('by_message', ['messageId'])
.index('by_user_and_chat', ['userId', 'chatId'])

// Resolves library labels for the source turn plus three later user turns, then
// deletes them. Cascades with its source message and under both chat-deletion
// paths; daily cleanup purges all remaining references for the completed chat.


dailySummaries: {
  chatId               // FK -> chats
  userId               // FK -> profiles
  date                 // string "2026-06-29"
  content              // string, narrative journal entry
  profileUpdated       // boolean; true only when the daily-cleanup response
                       // contains an approved typed profile patch
  profileUpdateNotes   // optional string; factual rationale for that patch
  createdAt            // number (timestamp)
}
.index('by_chat', ['chatId'])
.index('by_user_date', ['userId', 'date'])
.index('by_profileUpdated', ['profileUpdated'])

// CASCADE: intentionally SURVIVES the retention sweep — chatId is left
// dangling on purpose, standing on userId + date alone from that point
// on. This is deliberate, not a bug: the founder wants the journal to
// persist independent of the raw conversation. Cascades on force-delete
// (chats path 2) and on profiles deletion.


workoutContext: {
  userId                 // FK -> profiles
  content: { currentFocus, recentProgress, consistency, notableAchievements, considerations }
  triggerReason          // "daily-check"
                          // "session-close" removed — there is no separate
                          // session-close event anymore. A single hourly cron
                          // buckets users by profiles.timezone, finds zones at
                          // local midnight, and runs the daily-check for them —
                          // this same cron writes dailySummaries, conditionally
                          // appends workoutContext, and purges that day's
                          // sessionSummaries, all together.
  sourceSessionId        // optional FK -> sessions
  sourceDailySummaryId   // optional FK -> dailySummaries; the cleanup
                         // baseline. Later cleanup calls inject every retained
                         // daily summary after this row, with the three most
                         // recent available summaries always included, before
                         // deciding whether to append another context row.
  createdAt              // number (timestamp)
}
.index('by_user', ['userId'])
// Append-only, rolls over. No isCurrent flag. A null workout-context result
// does not append a row; daily summaries continue accumulating from the last
// row's sourceDailySummaryId.

// CASCADE: cascades on profiles deletion. sourceSessionId can never
// dangle since sessions are never deleted by the app.


sessionSummaries: {
  chatId          // FK -> chats
  content         // string
  tier            // 1 | 2
  compressedTill  // number (timestamp) — the last raw message covered by
                  // this summary, cumulative across tiers. Replaces the old
                  // compressCount, which was unneeded duplication of the
                  // same information.
  order           // number
  createdAt       // number (timestamp)
}
.index('by_chat_and_tier', ['chatId', 'tier'])
// Ephemeral — purged at the app level once a chat's dailySummaries entry
// is written (same daily-check cron, see workoutContext note above).
// Tier 1 rows are built from each source message's ordered text/tool-summary
// history; tier 2 compacts tier 1 summaries and therefore retains material
// tool outcomes transitively.

// CASCADE: deleted under BOTH chats deletion paths (sweep and force-delete).


apiUsage: {
  userId      // FK -> profiles
  timestamp   // number
  tokensUsed  // number
}
.index('by_user_time', ['userId', 'timestamp'])

// CASCADE: cascades on profiles deletion.
// Never fetched for or included in Gemini context — the one exception to
// the messageBlocks reversal above; token/cost records stay backend-only.


guideInvocations: {
  userId      // FK -> profiles
  messageId   // FK -> messages
  reviewed    // boolean, default false
  createdAt   // number (timestamp)
}
.index('by_user', ['userId'])
.index('by_message', ['messageId'])

// Backend-only. Never sent to Gemini, following the same exception pattern as
// apiUsage. Written once after each get_new_exercise_guidance execution — not
// model-invoked and not part of any
// tool's return schema.
// Purpose: safety/tuning review log for guide invocations, not a live-state
// tracker. It does not answer whether a naming-guide conversation is active;
// that remains messages.usedTools per the existing lock.
// CASCADE: cascades transitively via messages -> chats -> profiles, under both
// chat deletion paths (sweep and force-delete), same as messageFeedback. If
// the messages cascade note is ever made explicit per-table instead of general,
// add guideInvocations there.


messageFeedback: {
  messageId   // FK -> messages
  userId      // FK -> profiles
  rating      // "up" | "down"
  comment     // optional string, only when rating = "down"
  timestamp   // number
}
.index('by_message', ['messageId'])
.index('by_rating', ['rating'])
// No index on userId. The by_message index supports the development-only
// typed-confirmation delete control as well as the future review screen.

// CASCADE: cascades whenever its parent message is deleted — resolved
// this design session. Reasoning: messages are deleted as part of a chats
// cascade or by the development-only typed-confirmation debug control, and
// the intended v2 use of messageFeedback is a review screen pairing
// feedback with the message that caused it. An orphaned feedback row
// would be un-actionable, not merely unreferenced, and no confirmed use
// case pulls toward preserving it independently. Cascades under both the
// retention sweep and force-delete paths, and on profiles deletion.
//
// Contrast with userReports below: both are user-generated content tied
// to a userId, but the deciding factor was confirmed future use, not the
// field itself. userReports has a stated future use that depends on the
// id staying valid past deletion; messageFeedback's only stated future
// use (the review screen) actively requires the MESSAGE to survive
// alongside it — which cascading achieves — so there's nothing pulling
// toward messageFeedback outliving its message.


userReports: {
  userId     // FK -> profiles
  type       // "bug" | "feature" | "other"
  message    // string
  timestamp  // number
}
.index('by_type_timestamp', ['type', 'timestamp'])

// CASCADE: the SOLE EXCEPTION to the profiles cascade. userId is left
// dangling on profile deletion, deliberately: the founder wants to
// preserve per-user report counts (e.g. rewarding repeat bug reporters)
// even past account deletion, and report text may itself reference the
// user, so nulling it out would be both more complex and counterproductive.
```

## Development-only debug additions (2026-07-31)

The production schema contract above remains unchanged. When the development
debug console is enabled, `convex/debug/schema.ts` adds isolated diagnostics:
`debugConsoleApprovals`, `debugTurnEvents`, `debugReplaySnapshots`,
`debugReplayExperiments`, and `debugReplayResults`. They hold debug-admin
approval, sanitized traces, exact server-side Call 0 snapshots, and replay
results respectively. These tables are not product data, are never included in
Gemini context, and are removed with the development debug surface rather than
treated as a V1 product-schema feature.

Approved debug admins may also remove one message or force-delete one chat
through the development console only. Each action requires typed confirmation
and removes its diagnostics, replay artifacts, cards, and chat-scoped summary
rows according to the force-delete cascade. Confirmed workout sessions, blocks,
and exercises remain independent workout history.

## Tables removed / folded in

- **`userPreferences`** — folded into `profiles` (`weightUnit`, `darkMode`). Natural fit: same table, same query pattern.
- **`aiFeedback`** — **dropped entirely.** Was meant to log AI mis-parses and corrections tied to a `systemPrompt` version, for prompt-iteration analysis. On review this overlapped with `cards.rawOutput` / `cards.parsedData` / `cards.state`, which capture the same signal at the point of correction — except `cards` is ephemeral and doesn't preserve it long-term. Founder confirmed no intent to build correction-analysis tooling in v1, so the table was dropped rather than folded or kept dormant. Repurposing `cards` (which is designed to auto-confirm and often delete) into a permanent log would have fought its own design. If correction-analytics becomes a real feature later, it's a fresh design exercise, not a revival of this table.

## Cascade summary at a glance

| Trigger | Cascades |
|---|---|
| `profiles` deleted | Everything **except** `userReports` |
| `chats` retention sweep | `messages`, `cards`, `sessionSummaries`, `messageFeedback`, `guideInvocations` (transitively). **Not** `dailySummaries`. (Sweep itself is currently paused — see `chats` cascade notes above.) |
| `chats` force delete | Same as sweep, **plus** `dailySummaries` |
| `sessions` deleted | Never happens via app logic — manual/admin only, not a designed path |

## Parking lot — explicitly deferred, not forgotten

| Item | Why deferred | Notes for later |
|---|---|---|
| "Git-style" chat history | Judged unnecessary v1 complexity, reconfirmed v2 | Would require branch/parent pointers on `messages`/`chats` |
| Vector/semantic search over `messages`/`dailySummaries` | Not needed for v1 | Convex has native vector search — cheap to add later |
| `retainChatHistory` user toggle | Real feature, v2 decision | Would live as a `profiles` field; would trigger a purge job for that user's `messages` if off |
| Skills table (reusable procedures) | Prompt/config concern, not data-modeling | Only becomes a schema question if skills need to be editable without redeploying code |
| Importance-threshold-based reflection | Current after-session + nightly combo is reasonable for v1 | Possible v2 refinement, Stanford Generative Agents-style |
| `messageFeedback` aggregate analytics | Explicitly deferred — not worth designing at v1 when the feature is realistically v4 | If built, design its own retention-independent data needs fresh, rather than relying on rows that happened to survive `chats` cascades |
| Gemini-side prompt/context caching | Deferred post-v1 | Revisit once the static system prompt is finalized and its real token weight is known |
| Multi-card free-text "Ask Eco" (ambiguous card resolution) | Deferred to the pin feature | Explicit multi-select avoids the ambiguity of resolving free text against multiple pinned cards |
| Duplicate custom `exerciseLibrary` entries per user | Acknowledged gap, not a v1 fix | Pushed to v2 — dedup/merge strategy for near-identical custom rows |
